**Reading — descriptive, not a KPI scorecard.** Across a full CO2 severity sweep (1250–1775 ppm), the closed loop auto-closes 8/8 with zero human input, using a real planner (deepseek-v4-pro), a real Agentic RAG specialist loop, a real critic, and a real (simulated) actuator action. This is one domain, one anomaly type, at 8 severities — not 8 independent event types and not a 4-domain result, so it should not be read as "the system autonomously resolves IEQ incidents" in general; airquality is currently the only domain with an actuator (Phase 5 extends the other three). The other three domains (thermal/lighting/acoustic — no actuator exists yet) correctly halt at the `autonomy_gate` interrupt in 9/9 runs and never call an actuator regardless of severity — Hard Constraint #2 ("never bypass the autonomy gate") holds end to end, which is the more load-bearing claim of this table than the airquality auto-resolve count. The `co2_overcrowded` scenario (ventilation already at its ceiling, so no actuator sequence can succeed) is retried exactly `MAX_REPLANS`=2 times before honestly failing, every time — the closed-loop safety floor (a failed intervention triggers replan, not silence) holds under repetition, not just in the single anecdote Figure 21 already documents.

**"Verified 15 simulated minutes later" — cross-checked against Postgres, not just the in-graph field, because the in-graph field itself was found to be broken.** `ops/scripts/e2e_closed_loop_experiment.py`'s row extractor originally read `verifier_verdict`/`critic_approved` off the LangGraph state snapshot with an `isinstance(x, dict)` guard; `snap.values` actually returns live `VerifierVerdict`/`CriticVerdict` Pydantic instances, not dicts, so the guard silently failed and every row's `verifier_verdict` in the saved JSON reads `null` — including all 8 CLOSED rows. Rather than assert "verified" from a field that visibly reads null in the report a reader can open, we queried the production `incidents` table directly (verdict is written there independently by `agents/verifier.py::update_incident`, unaffected by the extractor bug): all 8 CO2 incidents show `verdict='met'`, `delta` between -179 and -225 ppm (CO2 dropped below target in every case). The extractor is fixed (`_verdict_field`, handles both shapes) for future runs. This is disclosed as a second methodological hazard (see below), not smoothed over.

**Methodological hazards found and fixed while building this table — worth stating plainly.** Three bugs surfaced during this experiment, all corrected before/alongside the numbers above:
1. An early severity sweep for thermal used 27/29/31°C — all *inside* the exhibit's actual deployed threshold (`sensing/thresholds.py` widens the ceiling to 32°C for the unconditioned summer room, not the WELL corpus's 21–25°C comfort band used elsewhere in this dissertation). None of those anomalies fired the Monitor at all. Fixed by re-checking the deployed threshold and using 33/35/37°C.
2. Tier-3 incidents never reach a terminal ticket status (no actuator exists to close the loop), so `mcp-ticket-server`'s sensor-keyed dedup (`active_incident_for_sensor`, correctly designed to stop a persistent anomaly spamming a new incident every 5-min scan) blocked every severity after the first from opening a fresh incident. Fixed with an explicit test-harness step that resolves the previous incident before arming the next severity — a concession for this experiment, not a change to the dedup logic itself, which is correct production behaviour.
3. The `verifier_verdict`/`critic_approved` extraction bug described above — found only because a reviewer asked "does 'verified' actually check out against the raw data," which it did not until cross-checked against Postgres.

**Honest limitations:** n is modest (20 incidents, one severity range, one domain with a real actuator); `co2_overcrowded` and the Tier-3 gate are single-scenario stress tests, not a broad sweep of every way an incident could be unfixable; this run writes real rows to the dev Postgres `incidents` table and the Qdrant `ieq_incidents` collection (author-approved), so the episodic store now also contains this run's synthetic incidents alongside prior dev-testing data — disclosed, not a claim of production operating history. This table is the primary evidence for H3's autonomy claim; Table 6's scheduling-model comparison should be read as a subordinate abstraction (it establishes an upper bound on what continuous polling buys over intermittent human checking) rather than co-equal evidence — it contains no LLM and cannot speak to whether the real system closes the loop.
